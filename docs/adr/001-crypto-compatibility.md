# ADR-001: Crypto Compatibility Strategy for Rust Rewrite

- Status: Proposed
- Date: 2026-03-11
- Deciders: Development Team
- Technical Area: Cryptography, Security
- Related Docs: `docs/rust-rewrite-guide.md`, `internal/crypto/crypto.go`
- Related Issues: Rust rewrite Phase 0.1

## Context

The Rust rewrite of `pyx` must maintain compatibility with existing encrypted data created by the Go implementation. The Go code uses `filippo.io/age` with scrypt-based encryption, but with a critical quirk:

**The Core Problem:**
- Go's `age.NewScryptIdentity()` and `age.NewScryptRecipient()` accept `string` parameters
- Go strings can hold arbitrary bytes (including invalid UTF-8)
- Rust's `String` must be valid UTF-8
- The Go implementation converts raw 32-byte master keys directly to strings: `string(key)`

This creates a compatibility challenge: can Rust's age implementation decrypt data encrypted with arbitrary byte sequences that may not be valid UTF-8?

**Current Go Behavior:**
1. Master key: 32 random bytes generated by `crypto/rand`
2. Encryption: `age.NewScryptRecipient(string(key))` - converts bytes to Go string
3. Decryption: `age.NewScryptIdentity(string(key))` - same conversion
4. Provider keys: Encrypted using master key bytes as passphrase

**Why This Matters:**
- Users have existing `master.key` and `database.json` files
- Forcing migration would break user trust and require complex migration tooling
- Strict compatibility is preferred per the rewrite guide

## Decision

**REVISED (2026-03-11): Use Option C: One-Time Migration with Go Tool**

Based on the Phase 0.1 crypto spike results:
- ✗ Rust age crate CANNOT directly decrypt Go-generated age ciphertexts
- Error: "Header is invalid" when attempting decryption
- Root cause: Age scrypt implementation differences between Go and Rust

**Migration Strategy:**
1. Create Go-based migration tool (`pyx migrate`)
2. Tool reads existing Go-encrypted data
3. Decrypts using Go implementation  
4. Re-encrypts using Rust-compatible age format
5. Rust implementation uses standard age scrypt APIs
6. One-time migration required for existing users

**Rationale:**
- Direct compatibility proven impossible with current approach
- Migration tool is one-time cost vs permanent runtime dependency
- Allows Rust implementation to use idiomatic age APIs
- Cleaner long-term maintainability
- Users only migrate once, then have pure Rust experience

## Alternatives Considered

### Option 1: Pure Rust age compatibility (CHOSEN)

**Approach:** Use Rust age crate's low-level APIs to replicate Go's byte-level behavior.

- Pros:
  - Clean Rust-only implementation
  - No external dependencies at runtime
  - Best long-term maintainability
  - Preserves strict compatibility goal

- Cons:
  - High risk - may not be possible if Rust age enforces UTF-8
  - Requires deep dive into age protocol internals
  - May require unsafe code or workarounds

### Option 2: Go compatibility shim

**Approach:** Keep a minimal Go binary for crypto operations only, call from Rust via CLI or cgo.

- Pros:
  - Guaranteed compatibility
  - Fast implementation
  - No cryptography reimplementation risk

- Cons:
  - Requires Go runtime for migration
  - More complex build process
  - Defeats purpose of Rust rewrite
  - Performance overhead

### Option 3: One-time migration with format change

**Approach:** Read old format with Go helper, re-encrypt with Rust-native format.

- Pros:
  - Clean Rust implementation going forward
  - Can fix any design issues in crypto layer
  - No long-term compatibility burden

- Cons:
  - Requires migration step
  - Risk of data loss during migration
  - User friction
  - Requires maintaining migration code path

### Option 4: Lower-level cryptographic primitives

**Approach:** Reimplement age scrypt protocol using raw crypto primitives in Rust.

- Pros:
  - Full control over byte-level behavior
  - No dependency on age crate limitations

- Cons:
  - High implementation complexity
  - Security audit required
  - Reinventing well-tested cryptography
  - **Strongly discouraged** - cryptography should use established libraries

## Consequences

### Positive

- Maintains user trust through seamless compatibility
- Achieves Rust rewrite goals without Go dependency
- Documents crypto compatibility risks early
- Forces early validation of highest-risk technical area

### Negative

- May require unsafe Rust or workarounds if age enforces UTF-8
- Crypto spike may fail, requiring replanning
- Additional complexity in crypto module

### Neutral

- Decision is reversible through migration path if needed
- Implementation can be isolated and replaced if compatibility proves impossible

## Notes

**Key Technical Insight:**
The age scrypt encryption process is:
1. Derive encryption key from passphrase using scrypt
2. Use derived key for actual encryption

The critical question is: does scrypt in Rust's age implementation accept the same byte sequences as Go, even if they're not valid UTF-8?

**Research Needed:**
- Examine Rust age crate's `scrypt::Identity::new()` implementation
- Check if it accepts arbitrary bytes or enforces UTF-8
- If UTF-8 enforced, explore if we can replicate scrypt derivation ourselves

**Fallback Position:**
If Rust age absolutely requires UTF-8 strings, we can:
1. Use raw scrypt to derive keys from bytes (bypassing age's string requirement)
2. Use age's lower-level encryption APIs with pre-derived keys
3. This maintains wire compatibility while working around string limitations

**Security Note:**
This ADR does not propose changing the cryptographic algorithm or key sizes - only ensuring Rust can work with the same byte sequences as Go. Security properties remain identical to Go implementation.
